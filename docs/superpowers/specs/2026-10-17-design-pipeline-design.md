# Design pipeline: impeccable visuals, fewer clicks, API after screens

Status: draft, 2026-10-17. Branch `feat/DesignPipeline`, cut from `origin/main`
at `e6d407d` (v0.8.0). Sub-project 2 of 4 in the Bearing improvement
programme (sub-project 1 shipped as v0.8.0). The user skipped the
brainstorming questions; every choice below not quoted from the user is
marked as the author's call.

## Intent

The user's feedback, points 2 to 4:

- (2) "Impeccable skills are good. Bearing design is not up to the mark.
  Although bearing is good at generating and maintaining the artifacts like
  design system, designs for all states, overall design is not great. We need
  to use impeccable for the better designs."
- (3) "All apps generated by bearing have complex userflows where end users
  need to navigate more and have to do more clicks. UX has to be optimised."
- (4) "It is better to design APIs after the UI/UX designs. Because APIs
  change based on the user flow, UI/UX. Right now in workflow API design
  comes first."

So: Bearing keeps what it is good at (flows, every state of every screen,
tokens, bindings, lints and contrast gates) and hands the visual judgement to
impeccable; flows get a measurable budget for steps and clicks per task; and
the API contract and data model are derived from the screens instead of
coming before them.

## Goals

1. Visual quality comes from impeccable wherever a Bearing skill chooses or
   judges visuals (direction, screens, critique), and Bearing's artifacts and
   gates still apply to the result.
2. Every primary task in a flow has a counted path (screens and
   interactions from entry to success) checked against a budget, and the
   flow pattern that most often inflates it is called out.
3. In both the greenfield and feature flows, screens come before the API
   contract and the data model, and those two skills take the screens'
   data needs as input.

## Non-goals

- No change to tokens, bindings, `design-lint`, contrast or state gates
  beyond what the three goals need.
- No new UI framework or component library.
- No rewrite of impeccable or vendoring of its files into Bearing.
- Sub-projects 3 (testing and review phases) and 4 (GenAI) are out of
  scope.

## Anti-goals (a failure even if it works)

- A design step that blocks or asks a question in an unattended autopilot
  run.
- Two design systems: impeccable's `DESIGN.md` and Bearing's `tokens.json`
  must not drift apart; one is the source, the other derived and checked.
- A click budget so strict that it pushes safety confirmations or required
  context off the path. A destructive or irreversible action keeps its
  confirmation; the budget counts it and allows it.
- An API that the screens cannot be built against: every screen state that
  needs the server maps to an operation and response.

## Constraints

- Everything from v0.8.0 holds: no em dashes; gates fail on zero input and
  print counts; SKILL.md at most 200 lines (or its allow-list ceiling);
  questions follow `plugins/bearing/references/console.md`; commands a
  skill runs are granted in `allowed-tools`; bash 3.2 portable scripts;
  Bearing never pushes.
- Impeccable is an external pack (`pbakaus/impeccable`, Apache-2.0,
  installed with the skills CLI as `impeccable`, invoked as `$impeccable
  <command>`). It asks questions; its own rule is to infer from the explicit
  brief and label inferred facts when no one can answer. It writes
  `PRODUCT.md`, `DESIGN.md` (with a sidecar) and `.impeccable/config.json`.
- Every external fetch is pinned in `plugins/bearing/bin/pinned-packs.txt`
  (`tests/unit/pins_match.sh` enforces it).
- Bearing must still work when impeccable is not installed (a fork, a
  minimal profile): the skills fall back to today's behaviour and say
  "impeccable not installed" once.

## Design

### A. Impeccable does the visuals (goal 1)

**A1. Install and pin.** Add a `cli|pbakaus/impeccable|<full commit>||impeccable|Apache-2.0`
row to `pinned-packs.txt` (author's call: commit `08d5b470495d242ca0470f4aeae1956c3a074f83`,
HEAD on 2026-10-17, to be confirmed as v4.5.2 or later at implementation).
`brg-install-packs` installs it in the standard and full profiles (author's
call: visual quality is the point of the request, so it is not full-only).
`docs/THIRD_PARTY.md` and `docs/known-skills.txt` list it; `brg-doctor`
reports it like the other packs.

**A2. One source of visual truth.** Impeccable's `DESIGN.md` is the visual
direction (prose, the palette, type, layout rules, voice). Bearing's
`docs/design/tokens.json` is derived from it by `design-system` and is what
code binds to. `design-system` records in `tokens.json` the `DESIGN.md`
content hash it was derived from; a check in `design-lint` (or a new
`design_sync_check`) fails when `DESIGN.md` changed after the tokens were
derived, printing both hashes. When the repository already has a
`docs/design/DESIGN.md` written by Bearing, it stays the file; impeccable is
pointed at it (author's call: one `DESIGN.md`, at the path Bearing uses,
with impeccable's sidecar beside it if it writes one).

**A3. Where each Bearing skill calls impeccable.**

| Bearing skill | Before | After (impeccable installed) |
|---|---|---|
| `design-directions` | Bearing's own doctrine picks palette, faces and layout for three variants | Run `$impeccable init` (once: `PRODUCT.md`) then impeccable's direction work (`shape` or new-work) for each of the three variants, so each variant is an impeccable direction; Bearing still renders them over real screens, scores them with its evidence gates and records `approved.json` |
| `design-system` | Tokens from a direction or brief | Tokens derived from the approved `DESIGN.md`; hash recorded (A2); bindings, contrast and lint unchanged |
| `screen-design` | Screens built to Bearing's doctrine | Screens built against the tokens and every flow state as today, then a `$impeccable polish` pass per screen set (and `$impeccable harden` for empty, error and loading states); Bearing's state, gallery, contrast and lint gates run after polish |
| `design-critique` | Bearing's 11-category checklist | `$impeccable critique` and `$impeccable audit` findings are folded into the review, each kept with its source; Bearing's measured checks (contrast pairs, widths, themes, copy against flows) stay |

`design-doctrine.md` stays as the fallback when impeccable is absent.

**A4. Unattended runs.** Under autopilot's unattended mode, each skill passes
impeccable the explicit brief and the flows and lets it infer, then records
in the skill's report which facts impeccable inferred (impeccable labels
them). No question reaches the user in that mode.

### B. Fewer clicks (goal 2)

**B1. Task paths in `ux-flows`.** `flows.md` gains a `## Task paths`
section: for each primary task (one per story the flows cover, or per
"job" when there are no stories), a row with the task, the entry screen,
the ordered screens and interactions to success, and the counts:
`screens`, `interactions` (taps, clicks, typed fields counted once per
field, selections). Author's call on the default budget per primary task:
at most 3 screens and at most 6 interactions from entry to success, not
counting typing the content itself; a secondary task (settings, admin) at
most 5 screens and 10 interactions. A repository can set its own budget in
`.bearing/config.json` (`ux.budget.primary.screens`, and so on) through
`brg-config`.

**B2. The gate.** `flows_check.py` parses `## Task paths`, recomputes the
counts from the listed steps, and fails a task over budget unless its row
carries `over: <reason>` (a legitimate reason: a legal confirmation, a
payment step the provider owns, a destructive action's confirmation). It
also fails when a primary task listed in the inventory has no path, and on
zero tasks. It prints `task paths: N tasks, M over budget (K with reason)`.

**B3. Patterns the skill steers away from.** `ux-flows` names the
patterns that inflate paths and what to do instead, each as one line:
a confirmation on a reversible action (undo instead); a separate page for a
short create or edit form (inline or a sheet); a wizard for under five
fields (one form); navigating away to pick a related item (inline picker);
an empty state with no primary action (put the action in it); a success
page that is a dead end (return to the list with the new item highlighted).
`design-critique` scores task cost from the same table (a category, author's
call: "task cost", counted, not judged).

### C. API after screens (goal 3)

**C1. Order in the flows.** In `docs/flows.json`:
- greenfield becomes high-level-design, then ux-flows, design-directions,
  design-system, screen-design, then data-model, openapi-spec,
  threat-model, then low-level-design and the rest as today. High-level
  design stays first because it sets the system boundaries the screens live
  in.
- feature: the branch that asks what the change needs keeps its options,
  but when a change has screens, the screens option comes first and the API
  and data-model options say they take the screens' data needs.
- `bin/gen-guide.py` stage rows, `docs/WORKFLOW.md`, the handbook data and
  `plugins/bearing/bin/flow-steps.tsv` are regenerated (`make docs`).

**C2. Data needs from the screens.** `screen-design` writes
`docs/design/screens/<feature>/data-needs.md`: per screen, the fields shown
(name, type, where they come from), the actions (what the user does, what
must happen on the server), and the server outcomes each state needs (the
error codes and messages the flows' error rows name, empty and loading
conditions). A check (in `states_check.py` or a new `data_needs_check.py`)
fails when a screen in the inventory has no entry or an action has no
outcome, and prints counts. On a feature against an existing API,
`screen-design` reads the existing contract as today and marks each need
`exists` or `new`.

**C3. API and data model read the needs.** `openapi-spec` and `data-model`
take `data-needs.md` as an input: each action becomes or maps to an
operation, each field to a schema property, each error outcome to a
documented response. `openapi-spec` reports coverage (`data needs: N
actions, M mapped, K new operations`) and fails when an action maps to
nothing. Existing inputs (stories, HLD interfaces, code routes, ADRs) stay.

**C4. Autopilot.** `brg-autopilot` stage order moves `ux` before `design`
(where `design` holds data-model and openapi-spec). Where `ux` needs a
scaffolded app (react-shadcn gallery inside the app), the order is
`repos` before `ux`; the implementer checks what `repos` needs from
`design` and orders accordingly, and `tests/unit/autopilot_stages.sh` is
updated to the new order.

## Testing

- Unit tests for every new or changed check (`flows_check.py` task paths
  and budgets, `data-needs` check, `openapi-spec` coverage, the
  `DESIGN.md`/tokens hash check), each with a failing case first and a
  zero-input case.
- `tests/unit/autopilot_stages.sh` asserts the new stage order.
- Evals: `evals/<skill>/evals.json` gain cases for the changed behaviour of
  ux-flows (a task over budget), screen-design (data-needs written),
  openapi-spec (operations from data needs), design-directions (impeccable
  absent: fallback line).
- `make check` and `make gate` pass.

### D. Settled after the builder check (author's calls)

**D1. One direction round, impeccable's pick.** In attended mode
`design-directions` runs impeccable's direction work once (its assigned
direction plus challengers on its own decision page). The user's pick there
is recorded by Bearing in `docs/design/variants/<feature>/approved.json`
(source: impeccable, the picked direction's name and the challengers it was
chosen over). Bearing then renders the picked direction over the real
screens and runs its evidence gates; the board shows the evidence, not a
second choice. Three Bearing-built variants remain only in the fallback
(impeccable absent or unattended).

**D2. Unattended means no impeccable question.** Impeccable's direction and
init steps insist on a real answer round, so under autopilot's unattended
mode (and when `BEARING_NONINTERACTIVE` or `BEARING_AUTOPILOT` is set)
`design-directions` uses the fallback doctrine and says so. Only impeccable
commands that do not ask (`polish`, `harden`, `critique`, `audit`; the
builder confirms each against impeccable's references) run unattended.

**D3. Which `DESIGN.md`, and when.** With impeccable, the root `DESIGN.md`
in impeccable's format (YAML frontmatter tokens plus prose,
`.impeccable/design.json` beside it) is the source. It is written right
after the direction pick, in impeccable's `document` seed mode, so tokens
can be derived before screens. `design-system` then stops writing
`DESIGN.md` from its template (template kept for the fallback) and the
symlink is reversed: `docs/design/DESIGN.md` points at the root file.
`tokens.json` records the source hash; when impeccable later updates
`DESIGN.md` (its finish step after screens), the hash check fails and the
fix is to rerun `design-system`, which re-derives tokens without writing
`DESIGN.md`, so the check cannot loop.

**D4. Install in the standard profile.** `install.sh` installs impeccable in
standard and full (through `brg-install-packs` or a direct pinned
`npx skills` line, the builder's choice), minimal leaves it out. The pin is
a full commit; the version that commit carries is recorded in the row's
comment and in `THIRD_PARTY.md` (the installed copy reports
`scripts/VERSION` 0.1.14 and skill metadata 4.5.2; the builder records what
the pinned commit says).

**D5. Autopilot order.** The `design` stage today holds high-level design,
data model, API contract and threat model, and `repos` needs the
`repo-plan.json` high-level design writes. Split it: an `architecture`
part (high-level design, as now), then `repos`, `ux` (flows, direction,
system, screens), then a new `contract` stage (data model, API contract,
threat model, from data needs), then `lld` and the rest. Stage names are
the builder's call; the order is not.
