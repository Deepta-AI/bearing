# The workflow: every stage, one main skill, and the alternates

Each row is a moment in product development or implementation. The main
skill is the one recommended choice for that moment, whatever pack it
comes from; Bearing skills are main only where nothing better exists. The
alternate column lists what a developer may use instead. The tables, the
"How to read this map" notes and the skills map in the repository
template are generated by `bin/gen-guide.py` (`make docs`) from one
source, so the handbook, this page, `AGENTS.md` and `CLAUDE.md` never
disagree. Every Bearing skill is explained in [SKILLS.md](SKILLS.md);
every pack, with its install command and licence, in
[THIRD_PARTY.md](THIRD_PARTY.md); the tracker the ticket rows talk to in
[TRACKERS.md](TRACKERS.md).

## How to read this map

- One main per row. The Skill column names exactly one skill; everything else a developer may use for that step is in the Alternate column, whatever pack it comes from. A Bearing skill is main only where nothing better was found.
- analytics-events serves two rows: under Set up the repository it designs the sheet and wires the SDK once; under Build a task it adds one feature's events against that sheet. Same skill, two moments.
- explain-codebase serves two rows as well: Discover (a repository you do not know) and Build a task (the subsystem you are about to change).
- tracker-sync appears under Plan and under Ship: ticket creation first, then the status and the MR link. With BEARING_TRACKER=none both rows are skipped with a note; rest (any server speaking the REST tracker protocol) is one adapter among none, jira, gitlab and github (docs/TRACKERS.md).
- Design review has two mains by time, not by taste: design-critique while only prototypes exist, gstack /design-review once the app runs in a browser.
- "Not this": an alternate marked (not installed) is documented with its install command in docs/THIRD_PARTY.md and is not fetched by the installer; an alternate that says "stops at the push" or "needs a key" carries that limit for a reason.

## One task, end to end

TASK-142: "Lock the account after five failed OTP attempts."

1. `start-task TASK-142 OtpLockout` creates `feature/TASK-142-OtpLockout`
   and the state file. The tracker is whatever `BEARING_TRACKER` names; with
   `none` the id is simply the one the team chose.
2. The story exists (from `backlog`); its criteria name the lock time
   and the admin unlock. `test-cases` writes `TC-0231` to `TC-0236`
   against those criteria.
3. The lockout screen is new, so the design lane runs once:
   `ux-flows` (states for the locked screen), `design-directions`
   (three variants, one chosen), `screen-design` (the screen with
   every state), `motion-design` for the lock moment, `design-critique` on
   the prototypes, and `/design-review` once the app runs.
4. `tech-decision` confirms a lockout table over a counter column;
   `adr` records it; `analytics-events event otp_locked`.
5. `db-migration add_otp_lockouts`; `test-driven-development` drives the
   service and handler; the hooks format every file; the Go rules loaded
   when the first `.go` file was touched. `logging` adds the entry and
   exit logs on the new handler.
6. `test-automation` generates the automated tests named with their
   TC ids; `test-run` produces the pass/fail report; one test drifts
   on a renamed button and `test-heal` repairs the locator, re-runs
   it, and leaves the one real regression red.
7. `definition-of-done`, then `branch-review`, then the harness's security review (auth
   changed), then `traceability` (zero gaps).
8. `merge-request` fills the merge request or pull request; the engineer pushes
   and opens it. `tracker-sync update TASK-142 --status "In Review"` and
   `tracker-sync trace TASK-142 --mr <url>` link it, or print
   `tracker: none` and skip.
9. Merge. `runbook OtpLockoutSpike` before the alert goes live.

A recorded build of one task lands in `docs/examples/walkthrough.md` and
is rendered into the handbook's "Worked example" section by `make docs`.

## Rules the workflow never bends

- The agent never pushes, merges, tags, deploys or opens a merge request
  or pull request. Hooks and permissions enforce it.
- No technology is chosen silently. `tech-decision` shows the options and a
  recommendation; the user decides; an ADR records it.
- Every gate fails on empty input and prints what it checked.
- Reviews are local. There is no AI review job in CI.
- Every artifact carries the ids it derives from; `traceability`
  proves the chain.
- Every skill works on its own: it declares its inputs and falls back to
  asking or deriving instead of depending on another skill having run.
- One task per session. `session-handoff` before pausing.
