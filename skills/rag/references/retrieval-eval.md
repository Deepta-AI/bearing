# Retrieval evaluation

Two layers. Retrieval metrics need only the golden set and the index.
Answer metrics need a model and go through `llm-eval`.

## Golden set

`evals/<name>/retrieval.jsonl`, one line per question:

```
{"id": "q-001", "question": "...", "relevant_chunk_ids": ["..."], "reference_answer": "...", "source": "user-log | owner | synthetic", "tags": ["billing"]}
```

- At least 30 questions. Fewer than 30 gives a recall figure that
  moves by 0.03 when one case flips.
- Sources in order of value: real user questions (PII removed), the
  corpus owner's questions, synthetic questions generated by
  `claude-sonnet-5` from a chunk (mark them; they are easier than real
  ones and inflate recall).
- `reference_answer` keeps the answer the owner confirmed, when one was
  given. Retrieval metrics ignore it; `llm-eval` grades correctness
  against it, and dropping it at this step loses it.
- Unanswerable questions stay in the set with an empty relevant list.
- `relevant_chunk_ids` are the chunks a person confirmed answer the
  question. Chunk ids change when chunking changes; store
  `(source_uri, span)` alongside and re-resolve after re-ingest.

## Retrieval metrics

Run `retrieve(question, k=10)` for every question and compute:

| Metric | Definition | Target |
| --- | --- | --- |
| recall@5 | fraction of relevant chunks in the top 5, averaged | 0.7 |
| recall@10 | same at 10 | 0.8 |
| MRR | mean of `1 / rank` of the first relevant hit (0 when none) | 0.6 |
| empty rate | fraction of questions with zero hits above the floor | under 0.05 |
| p95 latency | retrieval only, no generation | under 200 ms |

Print the count of questions evaluated. Zero questions fails the run.
Report per tag as well; one weak tag hides behind a good mean.

Numbers measured on the questions used to tune chunking, tokenising or
weights are in-sample and optimistic. Say so in the report, or hold out
a part of the set that tuning never looked at and report both.

## Answer metrics (through llm-eval)

| Metric | Grader | Notes |
| --- | --- | --- |
| Faithfulness | judge with the hits and the answer: every claim is supported by a cited chunk | judge model stronger than the answering model; `claude-opus-5` for a Sonnet 5 answerer |
| Answer relevance | judge: the answer addresses the question asked | rubric, structured output |
| Citation precision | deterministic: every `[doc:chunk]` in the answer exists in the hits | free |
| Refusal correctness | deterministic on the questions whose relevant set is empty: the answer says "not in the documents" | needs 5 or more unanswerable questions in the set |

## Reading the misses

For every question below recall@10, print the question, the relevant
chunk text, and the top 3 returned. The pattern tells the fix:

- Relevant chunk is a fragment (no heading, half a sentence): chunking.
- Relevant chunk mentions the exact term but ranks low: add BM25
  (hybrid) or the term is in a table the splitter broke.
- Relevant chunk ranks 6 to 20: add a reranker.
- Relevant chunk needs the previous section: hierarchical.
- Two chunks needed from two documents: graph or agentic.
- Nothing relevant exists: the golden set is wrong or the corpus is
  missing the document; fix the set, do not tune the retriever.

## Make targets

```
eval-retrieval: ## recall@k and MRR on evals/<name>/retrieval.jsonl
	uv run python -m <pkg>.rag.eval --set evals/<name>/retrieval.jsonl --k 5 10
```

The command exits non-zero when the set is empty or recall@10 drops
below the last accepted baseline in `evals/<name>/results/` by more
than 0.05.
